### 되돌리면 안 되는 결정

- **생존율은 예측이 아니라 실측 폐업률 환산** `(1−분기폐업률)^12`, 3년 고정.

## 2. ✅ 예상 매출 과대추정 — 배포까지 반영 완료 (2026-08-04)

> **끝났다.** 분모를 전체 점포 수로 고치고 `valid_quarters: 1→2` 와 함께 재학습해
> ML 이 나이브 규칙을 이겼다. 브랜치는 `main` 에 병합됐고(cbaab3d),
> **서빙·웹 산출물 재생성과 웹 이중보정 제거까지 완료**했다 (상단 8/04 블록 참조).
> 상세: [MODEL-EXPERIMENT-REPORT.md](MODEL-EXPERIMENT-REPORT.md) §3~§4.
> 아래 5단계 중 1~5 전부 완료 — `correctStoreCounts()` 는 `readStoreCounts()` 로 대체됐다.

아래는 문제 발견 당시의 기록이다.

**현상**: 프랜차이즈 비중이 큰 업종에서 점포당 매출이 크게 과대.
업종 평균 부풀림 배수 — 편의점 3.10배 · 치킨전문점 2.23배 · 패스트푸드점 1.90배 (2025Q2 실측).
개별 상권은 더 크다: 동대문역사문화공원역 편의점 = 전체 22개(일반 1 + 프랜차이즈 21) → **22배**.

**원인**: 학습 타깃 `target_next_q_sales_per_store = 매출 ÷ 점포_수` 인데,
`점포_수`(`STOR_CO`)는 전체가 아니라 **일반(비프랜차이즈) 점포 수**다.
같은 이유로 `프랜차이즈_비율 = 프랜차이즈_점포_수 / 점포_수` 가 1.0 을 넘는다
(2025Q2 에서 1,554건, 최대 2,100%).

**현재 대응**: 점포 수·프랜차이즈 비율은 웹에서 역산 보정하고
(`lib/normalize.ts` 의 `correctStoreCounts()`) 보정 사실을 UI 3곳에 노출한다.
정적 산출물은 `유사_업종_점포_수` 를 직접 써서 애초에 올바르다.
**매출은 학습 타깃이라 웹에서 고칠 수 없다** — `scaleNote` 로 한계만 밝힌다.

**근본 해결** (팀원 합의 + 재학습):

1. `Commercial-AI-/src/features/build.py:99` — 프랜차이즈 비율 분모를 `유사_업종_점포_수` 로
2. `Commercial-AI-/src/features/schema.py` — 타깃 분모도 `유사_업종_점포_수` 로
3. `scripts/train_model.py` 재학습 → `models/sales_model.pkl` 갱신 (**기존 학습본 백업 먼저**)
4. `scripts/build_serving_table.py` + `tools/export_web_static.py` 재생성
5. `lib/normalize.ts` 의 `correctStoreCounts()` 제거 (이중 보정 방지) + `contracts.ts` 의
   `competition.correction` 정리

원본 데이터가 확보돼 있으므로 재학습이 가능하다. 아래 §3 과 함께 진행하면 좋다.

## 3. ✅ ML 열세 — 해소됨 (2026-08-03)

> **`ml_beats_baseline_on_test: true` 달성.** 원인은 §2 의 타깃 분모 오염 + 검증셋
> 1분기 과적합 두 가지였다. 아래에 적힌 "유력한 원인 두 가지"(수요 피처 부재 /
> 외부 피처 NaN)는 **실측에서 둘 다 기각**됐다 — 인구는 walk-forward ±0.03%,
> 외부는 0.5%(부동산은 역효과).
> 상세: [MODEL-EXPERIMENT-REPORT.md](MODEL-EXPERIMENT-REPORT.md) §5.

아래는 발견 당시의 기록이다.

`Commercial-AI-/models/model_metadata.json` → `"ml_beats_baseline_on_test": false`.
test MAE 13,776,289(LightGBM) vs **13,572,510**("지난 분기와 같다"). SMAPE·R² 도 베이스라인 우세.

정직하게 기록되어 있다는 점은 강점이지만, 모델 성능이 평가 항목이면 최대 리스크다.
`scripts/tune_model.py` 가 존재하나 **실행된 적 없다** (metadata 에 `tuning` 키 없음).

**유력한 원인 두 가지** (§6 과 함께 보라):

1. **수요 측 핵심 피처가 아예 없다** — 상주(주거)인구·직장인구·소득이 미수집이라 학습에
   들어가지 않는다. 상권 매출 예측에서 이건 표준 피처다
2. **있는 외부 피처마저 값이 NaN** — `sf_*`/`re_*` 6개가 비어 있어(§0 '자주 하는 오해')
   ablation 에서 채택된 피처들이 실제로는 정보를 주지 못한다

즉 §6 의 데이터 확보가 §3 개선의 전제 조건이다. §2 의 타깃 분모 수정과 함께 재학습할 것.

## 10. 🟡 모델 정확도 평가 계획 (2026-07-30 사용자와 논의·합의된 방법론)

배경: 사용자가 "모델 정확도를 어떻게 측정하면 좋냐"고 물어 정리한 내용. 새 세션이
평가 작업을 이어받을 때 이 프레임을 따를 것.

### 현재 채점 체계 (이미 있는 것)

`train_model.py` 가 시간 기반 홀드아웃(마지막 분기 = test)으로 채점해
`models/model_metadata.json` 에 기록한다. 현재 성적:
- 모델 MAE ≈ 1,378만원 (점포당 분기 매출) vs "지난 분기와 같다" 규칙 ≈ 1,357만원
- **모델이 베이스라인에 1.5% 열세** (`ml_beats_baseline_on_test: false`) — §3 과 동일 사안.
  정확도 논의에서 가장 중요한 한 줄이다. 재현: `tools/verify_model_issues.py`

### 현행 채점의 허점 4가지 → 보강 방향

1. **시험이 1회** (마지막 분기 하나) → **롤링 백테스트**: 21개 분기를 활용해
   "각 분기 시점으로 돌아가 다음 분기 예측 → 실제와 비교"를 반복, 분기별 성적 흐름을 본다.
   운영 중에도 분기마다 "지난번 예측 vs 새로 나온 실적" 자동 채점 가능(일기예보 적중률 방식)
2. **절대 오차(원)만 있음** → **상대 오차(MAPE 계열) 추가**: 10억 상권의 1,300만원 오차와
   3천만 상권의 1,300만원 오차는 다르다
3. **전체 평균 하나로 뭉뚱그림** → **업종별 채점**: §2(분모 오류) 때문에 프랜차이즈 비중이
   큰 업종(편의점 3.10배 부풀림)은 유독 크게 틀리고 한식은 멀쩡할 것으로 예상.
   업종별 MAE 는 §2 의 살아있는 증거이자 수리 전/후 비포·애프터 자료가 된다
4. **정답지 자체가 §2 로 오염됨** → 분모를 고치면 타깃 값이 바뀌므로 **수리 전/후 MAE 를
   직접 비교하면 안 된다.** 재학습 후에는 모델과 베이스라인 **둘 다** 새 타깃으로 재채점해
   그 안에서 비교할 것 (MODEL-REQUESTS §3 의 완료 기준과 연동)

### 서비스 관점 지표 (발표용으로 더 설득력 있음)

우리 상품은 원 단위 금액이 아니라 **추천 순위·등급**이다. 따라서
"지난 분기 시점의 추천 상위 N 상권이 실제 다음 분기에 상위였나"(적중률,
또는 순위 상관계수)를 별도로 측정할 것. 금액이 다소 틀려도 순위가 맞으면
추천 서비스로는 유효하다는 논리.
